Nota Metodológica & Mapeamento de Stack:

A auditoria avaliou o código-fonte real sem suposições conceituais. Em cada uma das cinco categorias essenciais, as verificações foram adaptadas à arquitetura do projeto:

  • 1. Banco Sem Tranca: Como o PostgreSQL não possui RLS ativado, o isolamento é lógico na camada de aplicação. Avaliamos se o farmaciaId extraído do token JWT pelo JwtAuthFilter é estritamente aplicado em todas as queries JPA e SQL nativas.
  • 2. Permissão no Navegador: Cruzamos todos os route guards do Angular (roleGuard) e blocos condicionais de UI com as anotações @PreAuthorize e rotas de SecurityConfig no Spring Security.
  • 3. IDOR: Percorremos sistematicamente cada rota com parâmetros de caminho ({id}, {clienteId}, {usuarioId}) para confirmar que nenhum recurso de outra farmácia pode ser lido, alterado ou excluído.
  • 4. Chaves Expostas: Verificamos logs de inicialização (System.out.println), arquivos de configuração (application.yml), segredos JWT, scripts de teste de integração (Karate) e variáveis do Docker/CI.
  • 5. Inputs Sem Tratamento (XSS & Spoofing): Auditamos o binding dos templates Angular (ausência de innerHTML) e a manipulação de cabeçalhos de rede não confiáveis (como X-Forwarded-For no rate limiter do login).
Auditoria realizada de ponta a ponta sobre o repositório ficha-digital.

1. Resumo Executivo e Métricas

O sistema demonstra maturidade técnica consistente em seus fluxos operacionais centrais: o isolamento de dados entre farmácias está implementado com rigor em todas as operações de clientes e movimentações financeiras, as senhas usam hash BCrypt com salt e o frontend Angular conta com proteções automáticas nativas contra XSS. Foram identificados, contudo, pontos de atenção em controles de infraestrutura, rate limiting e observabilidade que demandam remediação.

2. Pontos Fortes e Riscos Centrais

✓ Isolamento Multi-tenant Rigoroso Todas as operações em ClienteRepository, LancamentoService, PagamentoService e ExtratoController filtram obrigatoriamente por farmacia_id originado do JWT.
✓ Hashes de Senha Seguros (BCrypt) O Spring Security criptografa senhas com BCrypt de força 10. Em nenhum ponto da aplicação a senha transita em texto puro para o banco e os DTOs nunca expõem senhaHash.
✓ Fail-Fast no Segredo JWT O JwtService.java rejeita tokens caso a chave tenha menos de 32 bytes (256 bits para HMAC-SHA256), impedindo assinaturas vulneráveis a ataques offline.
✓ Proteção Automática Contra XSS O Angular 18 realiza escape contextual de variáveis em todos os templates. O código não utiliza innerHTML nem bypasses no DomSanitizer.
✓ Prevenção Contra SQL Injection Todas as queries (inclusive queries nativas com UNION ALL) utilizam binding de parâmetros nomeados JPA/Hibernate, inviabilizando injeção de comandos SQL.
✓ Controle de Concorrência com Lock Otimista A entidade Cliente utiliza anotação @Version para gerenciar atualizações simultâneas de saldo, impedindo condições de corrida de débito/crédito.

Riscos Centrais Identificados:

⚠ Spoofing de IP no Rate Limiter de Login O serviço de autenticação consome o cabeçalho X-Forwarded-For sem validação prévia de proxies reversos confiáveis e não aplica rate limit indexado por e-mail, permitindo ataques de força bruta contínuos.
⚠ Vazamento de Material de Senha em Logs O inicializador de banco emite via System.out.println o e-mail e os três primeiros caracteres da senha de produção do Super Admin no console do container.
⚠ Ausência de Camada de RLS no Banco de Dados Não há Row-Level Security no PostgreSQL. A integridade multi-tenant reside inteiramente no código Java. Qualquer query futura construída sem o filtro por farmácia acarretará vazamento inter-tenant.

3. Detalhamento Técnico dos Achados

1. Bypass de Rate Limiting no Login via Spoofing do Cabeçalho X-Forwarded-For

ALTA
backend/src/main/java/com/fichadigital/auth/AuthService.java:50-55, 73-77

Descrição: O método getClientIp() lê o cabeçalho X-Forwarded-For fornecido pelo cliente e extrai o primeiro endereço sem verificar se a requisição originou-se de um proxy reverso confiável. Além disso, o Bucket4j aloca buckets exclusivamente com base nessa string de IP.

private String getClientIp() { String xfHeader = httpServletRequest.getHeader("X-Forwarded-For"); if (xfHeader == null || xfHeader.isEmpty()) { return httpServletRequest.getRemoteAddr(); } return xfHeader.split(",")[0].trim(); }

Por que é explorável: Um atacante pode enviar requisições contínuas de login alternando o valor do cabeçalho (ex: X-Forwarded-For: 1.1.1.1, X-Forwarded-For: 1.1.1.2). Como o bucket é indexado por IP e não pelo e-mail alvo, o limite de 5 tentativas a cada 5 minutos é zerado a cada requisição, viabilizando ataques de força bruta ilimitados contra contas DONO e SUPER_ADMIN.

2. Vazamento de Prefixo de Senha de Produção do Super Admin em Logs / STDOUT

ALTA
backend/src/main/java/com/fichadigital/config/AdminInitializer.java:38-43

Descrição: Durante a inicialização da aplicação, o componente AdminInitializer imprime no console padrão os três primeiros caracteres da senha de produção configurada para o Super Admin e o endereço de e-mail.

String senhaPreview = adminPassword != null && adminPassword.length() >= 3 ? adminPassword.substring(0, 3) + "***" : "(vazia ou nula)"; System.out.println("[AdminInitializer] Email lido: " + adminEmail); System.out.println("[AdminInitializer] Senha começa com: " + senhaPreview);

Por que é explorável: Em ambientes de nuvem (Render, AWS, GCP), saídas de stdout são gravadas em agregadores de telemetria acessíveis a operadores e ferramentas terceiras. Expor o prefixo de uma senha reduz dramaticamente a entropia do segredo para tentativas de quebra offline (CWE-532).

3. Credenciais Padrão Conhecidas e E-mail de Admin com Fallback Inseguro

MÉDIA
backend/src/main/java/com/fichadigital/config/AdminInitializer.java:24-25, karate-config.js:13-14

Descrição: O AdminInitializer define como fallback o e-mail admin@fichadigital.com caso ADMIN_EMAIL não seja especificado. Ao mesmo tempo, o template .env.example e o arquivo karate-config.js documentam senhas estáticas padronizadas (SenhaForteDe16CaracteresOuMais!), as quais são copiadas para o arquivo .env no fluxo de CI.

@Value("${ADMIN_EMAIL:admin@fichadigital.com}") private String adminEmail;

Por que é explorável: Caso um deploy em staging ou produção omita as variáveis específicas, uma conta de administração global com credenciais previsíveis ou públicas poderá ser provisionada silenciosamente.

4. Ausência de Validação de Input em DTOs de Escrita de Clientes e Lançamentos

MÉDIA
ClienteController.java:91-97, AtualizarTelefoneRequest.java:7, LancarFiadoRequest.java:17,20

Descrição: O endpoint PATCH /clientes/{id}/telefone não contém a anotação @Valid no parâmetro de request, e os campos descricao e pessoaRetirou em lançamentos de fiado não possuem limites declarados de tamanho.

Por que é explorável: O envio de telefones com mais de 20 caracteres dispara uma DataException no PostgreSQL resultando em erro 500 no lugar de 400 Bad Request. Já a inserção de payloads massivos em descrições pode causar sobrecarga de memória e esgotamento de disco desnecessários.

5. Ausência de Trava de Auto-Operação e Auto-Exclusão no Painel de Administração

BAIXA
backend/src/main/java/com/fichadigital/admin/AdminService.java:101-115

Descrição: Os métodos alterarStatus e excluirUsuario não verificam se o usuarioId informado corresponde à conta do próprio Super Admin autenticado.

Por que é explorável: Um administrador pode inadvertidamente desativar ou excluir a si mesmo, ocasionando o bloqueio acidental (lockout) de todas as contas administrativas sem possibilidade de recuperação sem intervenção manual no banco.

6. Descompasso de Permissões entre Frontend e Backend para Perfil SUPER_ADMIN

INFORMATIVA
frontend/src/app/core/auth/role.guard.ts:18, FarmaciaController.java:45

Descrição: O roleGuard do Angular autoriza irrestritamente o acesso do SUPER_ADMIN a todas as páginas da aplicação, incluindo a rota /dashboard (exclusiva de farmácia). No entanto, o backend exige hasRole('DONO') e tenta invocar SecurityUtils.farmaciaId(), falhando com 403 e gerando NullPointerException se invocado diretamente.

--- ISSUE 1 ---
### [Segurança] Corrigir bypass de rate limiting no login via spoofing de X-Forwarded-For **Labels:** `security`, `severity:high`, `auth` #### Descrição do Problema O método `AuthService.getClientIp()` consome cegamente o cabeçalho HTTP `X-Forwarded-For` enviado pelo cliente. Além disso, o rate limiting do Bucket4j é indexado exclusivamente pelo IP retornado, em vez de aplicar bloqueio pelo e-mail do usuário que está tentando se autenticar. Um atacante pode alternar o cabeçalho `X-Forwarded-For` em cada tentativa de login e realizar ataques de força bruta ilimitados contra qualquer conta. #### Evidência - Arquivo: `backend/src/main/java/com/fichadigital/auth/AuthService.java:50-55, 73-77` ```java private String getClientIp() { String xfHeader = httpServletRequest.getHeader("X-Forwarded-For"); if (xfHeader == null || xfHeader.isEmpty()) { return httpServletRequest.getRemoteAddr(); } return xfHeader.split(",")[0].trim(); } ``` #### Impacto Quebra total da proteção contra força bruta e preenchimento de credenciais (*credential stuffing*) em contas privilegiadas (DONO e SUPER_ADMIN). #### Sugestão de Correção 1. Aplicar rate limiting composto indexado pelo e-mail do usuário (`email.toLowerCase()`). 2. Obter o IP remoto de forma segura sem confiar em cabeçalhos forjáveis a menos que a aplicação esteja atrás de um proxy reverso explicitamente configurado no Spring (`server.forward-headers-strategy: framework`). #### Critérios de Aceite - [ ] O Bucket4j aplica limite de 5 tentativas por 5 minutos por e-mail de destino. - [ ] Enviar requisições repetidas com `X-Forwarded-For` forjado para o mesmo e-mail resulta em HTTP 429 após 5 tentativas. - [ ] Testes automatizados cobrem a tentativa de bypass com múltiplos IPs forjados.
--- FIM ISSUE 1 ---
--- ISSUE 2 ---
### [Segurança] Remover vazamento de prefixo de senha do Super Admin no log/stdout **Labels:** `security`, `severity:high`, `secrets` #### Descrição do Problema O componente `AdminInitializer` imprime no `stdout` o e-mail do Super Admin e os três primeiros caracteres da senha real lida das variáveis de ambiente de produção durante o startup da aplicação. #### Evidência - Arquivo: `backend/src/main/java/com/fichadigital/config/AdminInitializer.java:38-43` ```java String senhaPreview = adminPassword != null && adminPassword.length() >= 3 ? adminPassword.substring(0, 3) + "***" : "(vazia ou nula)"; System.out.println("[AdminInitializer] Email lido: " + adminEmail); System.out.println("[AdminInitializer] Senha começa com: " + senhaPreview); ``` #### Impacto Vazamento de material de credencial em logs de container e plataformas de hospedagem (Render, CloudWatch), facilitando ataques de força bruta offline e violando o CWE-532. #### Sugestão de Correção Remover completamente os `System.out.println` que exibem detalhes do e-mail e da senha. Registrar apenas uma mensagem genérica via logger configurado: `log.info("Inicialização do Super Admin concluída com sucesso.");`. #### Critérios de Aceite - [ ] Nenhuma informação sobre a senha (nem mesmo prefixos ou máscaras) é emitida no console ou logs. - [ ] `System.out.println` substituído por logger SLF4J padrão. - [ ] O startup da aplicação em produção não gera saídas com dados sensíveis.
--- FIM ISSUE 2 ---
--- ISSUE 3 ---
### [Segurança] Adicionar @Valid e limites de tamanho em campos de clientes e lançamentos **Labels:** `security`, `severity:medium`, `validation` #### Descrição do Problema O endpoint `PATCH /clientes/{id}/telefone` recebe o corpo da requisição sem a anotação `@Valid` e o DTO `AtualizarTelefoneRequest` não possui validação de formato ou tamanho. Adicionalmente, campos de texto livre em `LancarFiadoRequest` (`descricao` e `pessoaRetirou`) não possuem restrição de tamanho máximo. #### Evidência - Arquivo: `backend/src/main/java/com/fichadigital/cliente/ClienteController.java` (Linha 91) - Arquivo: `backend/src/main/java/com/fichadigital/cliente/AtualizarTelefoneRequest.java` (Linha 7) - Arquivo: `backend/src/main/java/com/fichadigital/lancamento/LancarFiadoRequest.java` (Linhas 17 e 20) #### Impacto - Envio de telefone com mais de 20 caracteres estoura `DataException` no PostgreSQL gerando HTTP 500 em vez de 400 Bad Request. - Possibilidade de envio de cargas massivas em `descricao`, causando consumo excessivo de memória ou espaço em disco. #### Sugestão de Correção 1. Adicionar `@Valid` no `@RequestBody` de `atualizarTelefone`. 2. Adicionar `@Size(max = 20)` em `AtualizarTelefoneRequest.telefone`. 3. Adicionar `@Size(max = 255)` em `LancarFiadoRequest.descricao` e `pessoaRetirou`. #### Critérios de Aceite - [ ] Requisições com telefone > 20 caracteres retornam HTTP 400 com detalhe de validação RFC 9457. - [ ] Campos de descrição e pessoaRetirou rejeitam strings superiores a 255 caracteres com HTTP 400.
--- FIM ISSUE 3 ---
--- ISSUE 4 ---
### [Segurança] Implementar trava de proteção contra auto-desativação e auto-exclusão no Admin **Labels:** `security`, `severity:low`, `admin` #### Descrição do Problema Os endpoints de gerenciamento de usuários em `AdminService` (`alterarStatus` e `excluirUsuario`) permitem que qualquer Super Admin altere o status ou delete o seu próprio usuário (`usuarioId == usuarioAutenticado.getId()`), ou a conta principal criada pelo inicializador. #### Evidência - Arquivo: `backend/src/main/java/com/fichadigital/admin/AdminService.java:101-115` #### Impacto Risco de lockout permanente da administração do sistema por erro operacional ou manipulação acidental de requisição. #### Sugestão de Correção Validar se `usuarioId.equals(SecurityUtils.usuarioId())` e lançar `IllegalArgumentException("Não é permitido alterar o status ou excluir o próprio usuário logado.")`. #### Critérios de Aceite - [ ] Tentativa de auto-desativação do usuário logado retorna HTTP 409 Conflict com mensagem explicativa. - [ ] Tentativa de auto-exclusão do usuário logado é bloqueada. - [ ] Outros usuários continuam podendo ser ativados/desativados normalmente.
--- FIM ISSUE 4 ---
